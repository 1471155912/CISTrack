一个**纯前端、无服务端**的中国低轨互联网星座追踪页，用真实的公开轨道数据（NORAD 目录 / TLE）在浏览器里实时推算并可视化：

- **星网（国网 / GW / GuoWang / SatNet，代号 CSCN）** —— 中国卫星网络集团
- **千帆星座（千帆 / Qianfan / Thousand Sails / SpaceSail，G60）** —— 上海垣信卫星

### 先把这个项目的形态说清楚（避免误会）

它**没有服务端后端**（无账号、无数据库、无 API 服务器、不上传任何用户数据），但**也不是"只要一个文件、其余什么都不需要"**。
现在有两种形态：

| 形态 | 是什么 | 你需要什么 |
|---|---|---|
| **① 单文件**（最小形态） | 一个约 1.6 MB 的 `CISTrack.html`，卫星数据与海岸线都内嵌，**双击就能用、可完全离线** | 只要一个浏览器 |
| **② 完整形态**（数据能自动更新） | 仓库整体：HTML + `wiki.json` + `history/` 历史分片 + Node 构建链 + `deploy/` 一键更新与定时任务 | 浏览器；想自动刷新时再加 Node 18+ |

所以更准确的说法是 **「纯前端 + 可选的数据管线」**：

- **页面自己会联网**：打开时直接取最新 TLE，并从同目录（或官方 Pages）取百科统计；取不到就用内置快照。
- **想彻底离线 / 想数据最新**：用 `deploy/` 的脚本在本机刷新并重新打包（可注册每天定时任务）。
- **仓库侧**：GitHub Actions 每 12 小时刷新 TLE 并重新打包 —— 那是 **CI**，不是运行时后端。

打开一个 HTML 文件即可看到全部内容 —— **不需要服务器，也不需要你（使用者）构建**。

联网时页面会在浏览器里现拉最新的轨道要素、按需加载历史轨道分片，并读取同目录的 `wiki.json` 覆盖顶部统计数字；**完全离线也能打开**，此时改用打包时内置的快照与精简历史库，各章节照常可用。

> 非官方项目。数据来自公开的 NORAD 空间目标目录与卫星百科，仅用于科普与观测参考，**不适用于轨道预报、工程或研究用途**。

## ✨ 它有什么

| 章节 | 内容 |
|---|---|
| **01 地图** | 每颗卫星此刻的星下点、对地可视覆盖区（最低仰角可调）、前后各半圈地面轨迹，支持固定地面观测点并高亮可见卫星 |
| **02 轨道** | 3D 地球：轨道倾角、可视区域、不同批次轨道面的分离一眼可见（高度按 2.4× 夸张显示以便区分壳层） |
| **03 倾角分布** | 横轴 = 轨道倾角，纵轴 = 半长轴 / 远地点 / 近地点；一张图看清星座分布在哪些轨道面。数据同时跨 LEO 与 GEO 时启用**断轴**（LEO 上界与 GEO 下界在画布上对齐、中间高度视作不存在），两块区域是一张**连续**的图 —— 缩放平移整体联动，不会在交界处跳变 |
| **04 变轨情况** | 每颗卫星从入轨到工作轨道的**半长轴变化曲线**（自建历史轨道数据库驱动，选中批次/单星即画；已再入的卫星标红）。升轨速度 = ±2 天窗口最小二乘；**状态判据：|速率| > 0.5 km/天 记「点火」，≤0.5 且未进入工作高度带（±30 km）记「间歇」**（本章图下说明里有同一句标注）；**纵轴贴合所选批次的实际高度范围**（放大星间差异），横轴从发射日到数据末点；支持半长轴/升轨速度两种口径、导出图片带升轨速度列、与全局选中双向联动。**右侧标签用短名**（`A124`／`S03`／`G01`／`A27A`，中英同一套），**点标签即选中该星**（鼠标与触摸都可）并与其他章节联动；**正式全名**（百科词条名 / 英文 `WHJSW-编号`）在信息窗标题与卫星表格里给出，TLE 登记原名在「目录名」行 |
| **05 组网进度** | 两条累计曲线随时间（横轴按周、标注为对应日期）看星座建设节奏：**发射量** = 累计发射颗数（扣掉搭车星与同批 R/B），**在轨数量** = 已有 TLE 的颗数；三个时间段档（全部 / 今年 / 最近3月） |
| **06 卫星表格** | 全量在轨卫星的轨道要素（批次/组、制造方、**在轨状态**、半长轴、近远地点、倾角、周期、在轨天数、RAAN、偏心率、大气阻力系数、历元），可排序、可搜索、可导出图片。偏心率与大气阻力系数用**标准科学记数法**（`1.23×10⁻⁵`）。制造方取自卫星百科词条，收成简称并可点击跳转 |
| **07 发射历史** | 逐次发射的批次 / 运载火箭 / 发射时间 / 发射地点 / **目标倾角** / **发射卫星数** / 任务结果。卫星数写本星座的颗数，搭载了其它卫星时写 `M/N颗`；失败的行两列写 `-`。火箭与场地可跳转卫星百科，卫星名可跳转 satcat.com |

其它：中英双语、深浅主题、全屏（手机端自动横屏 + 常亮）、时间轴回放（±180 分钟，地图 / 轨道两章 × 星网 / 千帆四个组合各自独立，支持非线性平滑动画；实时态下「实时」按钮用**主题色填充并呼吸闪烁**、文字取主题前景色，被推离实时后转为**固定黄色状态灯**）、图→表联动、PNG 导出（带模拟时间与免责声明的底栏）。

## 🖥️ 本地部署（含定时自动更新）

除了"双击单文件 HTML"，你也可以把这整个仓库放到自己电脑上，**定期自动**拉最新轨道要素并重新打包。
适合想让数据始终最新、又不想手动下载的人。

### 前提条件

| 项 | 要求 |
|---|---|
| Node.js | **18 或更高**（<https://nodejs.org/>）。构建链**零 npm 依赖**，装完 Node 就能跑，不需要 `npm install` |
| 网络 | 只有"更新数据"那一步需要联网（访问 `celestrak.org`）；日常看图完全离线 |
| 磁盘 | 约 20 MB |

### 第一步：拿到仓库

两种方式任选：

- **下载 Release 的 zip**（[最新 Release](https://github.com/1471155912/CISTrack/releases/latest) 的
  `CISTrack_v1.9.8_local-deploy.zip`）→ 解压即用，**这是给本地部署准备的完整包**；
- 或 `git clone https://github.com/1471155912/CISTrack.git`

### 第二步：按需要选一种用法

#### A. 只用现成的页面（什么都不用装）

直接双击 `CISTrack.html`。页面自己会在打开时尝试联网更新，失败就用内置数据。

#### B. 想更新时手动更新一次

| 系统 | 命令 |
|---|---|
| Windows | 双击 `deploy\update.bat`（或命令行执行 `deploy\update.bat`） |
| macOS / Linux | `./deploy/update.sh` |

它会依次做四件事：拉最新轨道要素 → 重建内置数据 → 重新打包单文件 HTML → 同步版本快照。
跑完双击新的 `CISTrack.html` 即可。

#### C. 每天自动更新（定时任务）

| 系统 | 注册 | 取消 |
|---|---|---|
| Windows | 双击 `deploy\schedule-install.bat`（每天 06:00） | 双击 `deploy\schedule-remove.bat` |
| macOS / Linux | `./deploy/schedule-install.sh`（每天 06:00 写入 crontab） | `./deploy/schedule-remove.sh` |

Windows 上注册后可在"任务计划程序"（`taskschd.msc`）里看到名为 `CISTrack-Update` 的任务；
macOS/Linux 上用 `crontab -l` 查看。日志写在 `deploy/update.log`。

### 数据与隐私

- 更新时**只**访问 `celestrak.org`（公开的 NORAD 空间目标目录）与卫星百科；
  不上传任何东西，也没有账号、密钥或遥测。
- 页面**不写浏览器本地存储**：设置、视图、页码刷新即回到默认（这是有意的设计）。
- 定时任务只在本机执行，产出只写本机文件。

### ❓ 本地部署 Q&A

**Q1：没有 Node.js 能用吗？**
能。不装 Node 就等于"方式 A"——直接双击 `CISTrack.html`，页面打开时会自己联网更新。
Node 只在你想**重新打包**（把新 TLE 写进单文件）时才需要。

**Q2：定时更新失败了怎么办？**
绝大多数是当时网络不通（访问不到 CelesTrak）。这**不影响**已有页面：内置数据照旧工作，
页面打开时还会再试一次联网更新。想看原因就打开 `deploy/update.log`。

**Q3：更新后的页面覆盖了原来的吗？**
是。`deploy/update.bat` / `update.sh` 会重新生成 `CISTrack.html`（并留一份
`CISTrack_v<版本>.html` 快照）。想留旧版，更新前自己复制一份即可。

**Q4：为什么更新只要几秒，有时候却要几分钟？**
慢的时候通常是在等 CelesTrak 响应（它会自动重试几次）。构建本身是纯本地计算，几秒钟。

**Q5：能在服务器 / NAS / Docker 里跑吗？**
能，它就是"Node 脚本 + 静态文件"。把仓库放到任意目录，用 `deploy/update.sh` 更新，
再把 `CISTrack.html` + `wiki.json` + `history/` 用任意静态服务器（Nginx、`python -m http.server`）Serve 即可。
注意：若通过 `http(s)://` 访问，页面才能拉 `wiki.json` 与历史分片；`file://` 双击打开时这两项会被跳过
（卫星位置与要素不受影响，只影响顶部词条统计与 04 章历史曲线）。

**Q6：Windows 上双击 bat 窗口一闪而过？**
那说明它已经跑完了（成功或失败都会 `pause` 等你按键；若仍是一闪，请右键"用命令行运行"看输出）。
本仓库的 bat 已按 CRLF + 纯 ASCII 编写，避免编码问题。

**Q7：定时任务会不会很吵？**
不会弹窗（Windows 任务计划与 cron 都是后台执行），只在 `deploy/update.log` 里留日志。

## 🔄 更新数据

**方式一：只改统计数字（最省事，不需要任何环境）**

页面顶部的词条计数（已发射 / 在轨 / 发射成功）支持被同目录下的 `wiki.json` 覆盖。
把这个 JSON 和 HTML 放在一起（例如一起传到 GitHub Pages），以后只要编辑 JSON 里的数字并保存，**所有访客刷新就能看到新统计**。

```json
{
  "asOf": "2026-09-30",
  "gw": { "launched": { "n": 248, "...": "..." }, "inOrbit": { "n": 244 }, "launches": "40/41" },
  "qf": { "launched": { "n": 262 }, "inOrbit": { "n": 262 }, "launches": "19/19" }
}
```

> 为什么不做成页面自动抓取？卫星百科的 WAF 对非浏览器请求返回 403，且响应不带 CORS 头，浏览器里拿不到。所以采用「托管一份 JSON」这个折中。

**方式一之二：用脚本自动更新 `wiki.json`（零依赖，V1.7.0 二轮起）**

```bash
node scripts/fetch_wiki.mjs        # 起一个本机 Edge/Chrome 过 WAF → 解析统计 → 有变才写 wiki.json
```

- **零依赖**：只用 Node 自带能力（`child_process` + 内置 `fetch` + 内置 `WebSocket` 走 CDP），
  不再需要 `playwright`——所以在没有 `node_modules` 的环境（如纯计划任务）里也能跑。
- 浏览器可执行文件自动在常见路径里找；也可以用环境变量 `CISTRACK_EDGE` 指定（兼容旧名 `EDGE_PATH`）。
- 数字没变化时**不写文件**（便于 `git` 判断是否要提交）。
- 抓不到（WAF 不过 / 解析失败）会以**非零退出码**结束，方便计划任务与 CI 标红。

> 如果用计划任务自动运行这个脚本：任务里必须允许「用电池时启动」（`DisallowStartIfOnBatteries = false`），
> 否则笔记本一旦没插电，任务会被系统直接拒绝、静默不跑。

## 🔄 数据从哪来 · 怎么更新

**一句话结论**：轨道要素（TLE）由**访客自己的浏览器**在打开页面时现拉，所以在线访客看到的永远是最新；其余数据（卫星百科的统计与元数据、逐次发射的任务结果、海岸线、SGP4 实现）都在**构建时**抓取或打包进单文件。GitHub Pages 没有数据库，只能把仓库里的文件原样发出去，所以"网站数据更新"只有这两条路。

| 数据源 | 用来做什么 | 怎么更新 | 需要本地任务吗 |
|---|---|---|---|
| **CelesTrak / NORAD 轨道要素（TLE）** | 卫星此刻位置、地面覆盖、轨道形状 | **访客打开页面时在他自己浏览器里现拉**（多路查询 + 公共代理兜底 + 30 分钟会话缓存） | **不需要**（在线访客永远是最新） |
| **Space-Track GP 历史要素集** | **04 变轨情况**的半长轴爬升曲线（历史轨道数据库） | 构建时批量拉取（登录 + `gp_history` 查询，`format=tle`）注入 `data/history/`；`refresh.mjs` 日常追加当天要素；`mkdata.mjs` 采样打包成 `history/` 发布分片 | 本机任务（配额限制，不适合放 CI） |
| **卫星百科「星网 / 千帆星座」词条** | 页面顶部三个统计数字（已发射 / 在轨 / 发射成功） | 构建时抓一次打包；另可用计划任务定时运行 `scripts/fetch_wiki.mjs`（零依赖）自动抓取并提交 | 可选（只针对顶部数字） |
| **卫星百科「引导页:发射记录」年度页** | 发射历史章的「任务结果」列、05 组网进度的纵向口径 | 构建时运行 `scripts/fetch_launch_results.mjs` 抓取，写入 `wiki_launches.json` 后由 `mkdata.mjs` 合并 | 可选（建议与 TLE 任务一起跑） |
| **Natural Earth 海岸线** | 地图陆地轮廓 | 构建时下载并打包 | 不需要 |
| **satellite-js（SGP4）** | 从 TLE 推算位置 | 构建时打包 | 不需要 |

`data/ct_*.tle` 只是**离线兜底快照**，可以用 `refresh.mjs` 定期刷新。

**自动化（V1.8.0 起采用 A＋B 双轨）**

- **A · 本地计划任务**：`update_tle.bat` / `update_wiki.bat` 负责 `refresh → mkdata → build → build_release → git push`。
  - 每一步都查退出码，**失败自动重试最多 3 次**（间隔 90 s），全过程追加到 `logs/tle_refresh.log` / `logs/wiki_refresh.log`；
  - 两个任务**共用 `logs/git.lock` 互斥**（都在 00:00 与 12:00 触发），避免同时提交打架；锁超过 5 分钟视为陈旧并自动清除；
  - 推送前先 `git pull --rebase --autostash`（云端可能刚推过）；
  - 任务本身设了「错过就尽快补跑」，并把超时放宽到 TLE 2 h / 卫星百科 45 min，避免重试途中被硬杀。
- **B · TLE 链路搬上 GitHub Actions**（`.github/workflows/update-tle.yml`）：每 12 小时在云端跑一次
  TLE 刷新与重新打包（CelesTrak 不拦数据中心 IP）。**卫星百科那部分仍留在本机** —— 它要过
  Cloudflare 的 WAF，数据中心 IP 拿不到（`update-wiki.yml` 因此只保留手动触发）。
- 这样即使本机长时间关机，在线页面仍能拿到较新的 TLE；而词条统计与发射任务结果由本机补全。
- 访客打开页面时本来就会自己现拉最新 TLE，所以这两条链路保障的是**离线兜底快照**的新鲜度
  （最多旧半天），而不是在线访客所看到的。

## 🧩 它是怎么构成的

```
template.html   # 版式与样式（含内联的 Audiowide 字体）
app.js          # 全部逻辑：SGP4 推算、绘制、交互、i18n
data/           # satellite.min.js（SGP4）、海岸线、TLE 快照、NORAD 目录
mkdata.mjs      # 数据构建：TLE 按批次差分打包 + 词条元数据
build.mjs       # 把上面几块注入 template → 单文件 HTML
```

几个值得一提的设计：

- **轨道计算全在浏览器里**：用 satellite-js 跑 SGP4（WGS-72），零 API 调用。
- **TLE 按批次差分**：同一次发射的卫星两行要素大半字符相同，因此按 COSPAR 前缀做字符级模板，`satdata.json` 因此小了约 44%。
- **多源 TLE 合并**：CelesTrak 的分组会漏掉早期试验星，所以再加「按名称前缀查询」与「按编号反查」，同一颗取历元最新的一份。
- **只拿 HTML 也能用**：运行时联网取得的每一份数据都是增强而非前提 —— 断网时回落到打包内置的快照与精简历史库，各章节照常可用。

## 🗄️ 历史轨道数据库（V1.9.0 起）

**04 变轨情况**章的曲线由一份自建的历史轨道数据库驱动。设计目标是：随两个星座从几千颗涨到**数万、数十万颗**仍然可用，且能作为开源项目的一部分直接托管在 GitHub 上。

**数据从哪来**：Space-Track.org 的 **GP 历史要素集**（`class/gp_history`）——18 SDS 对每颗卫星逐日重发的多组轨道要素。脚本用官方账号登录后批量查询（10 颗/请求、按年分窗、`format=tle`），解析 TLE 的历元与平均运动，按**布劳威尔模型**反算半长轴（与页面 / SGP4 同一口径），每颗星从它发射后的第一条要素开始存。**只存布劳威尔半长轴**——一种模型、一个值，不混口径。

**结构（两层）**：

| 层 | 位置 | 格式 | 谁写 / 谁读 |
|---|---|---|---|
| 源库 | `data/history/<批次>.json` | v1 三元组 `[norad, 毫秒历元, 半长轴]`，每天 ≤2 条 | `refresh.mjs` 每天追加（幂等，按 (norad, 历元) 去重） |
| 发布库 | `history/index-*.json` + `history/<批次>-<链接号>.json` | v2 紧凑编码：norad 只存一次、天数相对化（`t0` + 偏移数组）、半长轴定点数（`base`+`prec` 写入分片头，防两端失配） | `mkdata.mjs` 采样打包；页面**按需加载**（首屏只取索引，选中批次才取分片，LRU 缓存 24 片） |

页面加载有**三级降级**：外挂发布分片 → 内置 60 天精简兜底（离线打开也有图）→「暂无历史数据」。

**容量为什么扛得住数万颗**：核心认识是「卫星到工作轨道后每天存点是纯浪费」。采样策略为**变化驱动 + 分层 + 稳定期配额**——升轨期（日变化 ≥0.05 km）密采，稳定期每月 1~2 点且每星最多 24 点。实测单星 1 年 244 点、**20 年只有 39 点**，每星约 440 字节；**10 万颗 × 20 年 ≈ 42 MB**（朴素逐日方案要 2.26 GB，缩 54 倍）。单个分片上限 4 MB，浏览器加载无压力。

**日常维护**：不需要人工干预——

1. `refresh.mjs`（本地任务每 12 小时）拉最新 TLE 时顺手把当天要素追加进源库；
2. `mkdata.mjs`（构建时）把源库采样打包成发布分片，随 `build.mjs` 一起复制到产物目录；
3. 源库有容量治理兜底（每星 ≤3000 点、单库 24 MB），永不无限膨胀；
4. 新批次发射后自动出现在索引里，无需改代码。

**如果某批卫星的曲线画不出来**（历史只有孤零零一两个点）：那是"历史过薄"，不是没有数据 ——
跑 `node scripts/fetch_history.mjs --missing` 补。它会**自动识别**"历史跨度小于其在轨期一半"的卫星，
并且**只查这些卫星自己的年份窗口**（实测 33 颗 → 13 次请求；相比之下老的 `--net` 会把
全部 50 个分块 × 整段年份重扫一遍，200~400 次请求）。加 `--net` 才真正联网（需要 Space-Track 账号，
凭据走环境变量 `SPACETRACK_USER` / `SPACETRACK_PASS`，不落盘）；不加则从 `data/history_cache/`
的原始报文池**离线**重算，0 请求。补完记得跑一次 `--prune` 做容量治理。

## 🧭 三种「高度」：各用在哪、怎么算（V1.9.8）

页面上出现的"高度"不是同一个量，**不要互相换算**。三者全部由公开 TLE 算出，不含任何人工填写的设计值；页面内「说明 → 科学口径 → 三种「高度」」有同一份说明。

**① 半长轴高度**（表格 / 图表纵轴 / 第 0 章「轨道分布」/ 04 章曲线）：`h = a_Brouwer − 6378.135 km`。`a_Brouwer` 是把目录平均运动剥掉 J2 长期项后的半长轴（WGS-72，SGP4 内部递推用的就是它），减去的是 WGS-72 赤道半径。它是**几何尺度**，与卫星此刻飞到哪个纬度无关。

**② 瞬时高度**（01 地图 / 02 地球的信息窗，每秒刷新）：**WGS-84 椭球面（海平面）以上的大地高**。算法：SGP4 给 ECI → ECEF → 由 `p=√(x²+y²)`、`z` 迭代反解**大地纬度** `φ`（Bowring 式，20 次迭代）→ `h = p/cosφ − N(φ)`，`N(φ)=a/√(1−e²sin²φ)`，`a=6378.137 km`、`b=6356.7523142 km`、`f=1/298.257223563`、`e²=2f−f²=0.00669437999014`。**不含**地形海拔、不含大气折射。

**③ 地心距**（只在内部用）：`r=|位置矢量|`。它与 ② 的差就是"地球不是球"。

**为什么 ② 会自己跳 20 多公里**：对圆轨道 `r` 几乎不变，但椭球面在极地比赤道**低 21.4 km**（`a−b`）—— 同一颗 1150 km 的星在赤道上空读约 1150、在极地上空读约 1171。这是几何事实，不是抖动；在此之上再叠加 **±a·e**（≈±1.4 km）。星下点纬度用的是**大地纬度**（不是地心纬度，两者在 45° 附近差约 0.19°）。**覆盖区 / 仰角 / 可视锥仍用地心球**（半径 6378.135 km）—— 那是一次有意的近似，10° 仰角下椭球带来的差异 <0.3%。

## 🧭 方法来源与致谢（V1.9.8）

本项目的**轨道计算 / 离地高度 / 星下点经纬度**在方法上参考了同题材的开源项目
**[findrassvet](https://findrassvet.ru)**（作者 V. Bulybenko，追踪 Бюро 1440 的「Рассвет」星座升轨过程），
其方法论公开在 [vbklgd/findrassvet · METHODOLOGY.md](https://github.com/vbklgd/findrassvet/blob/main/METHODOLOGY.md)。

具体采用的三条（每条都附了它给出的量化依据）：

| 采用点 | 为什么这么做（对方原文的数据） | 在本项目里的落点 |
|---|---|---|
| **半长轴走 Kozai→Brouwer**（复刻 `sgp4init` 的三步，WGS-72），而不是直接 `a=(μ/n²)^⅓` | 直接用平均运动算，在 **82.3°/97.4° 倾角上系统性偏高 +3.03/+3.04 km**，51.6° 只偏 −0.50 km | 本项目的「计算模型」默认就是 **Brouwer**，与此一致 |
| **升轨速率用 2 天最小二乘窗**，绝不用相邻元素集差分 | 单点拟合噪声 σ=0.166 km、元素集中位间隔 7.5 h → 相邻差分噪声 ≈ **0.75 km/day**，足以让被动飞行（−0.05 km/day）看起来像在推；改用 2 天窗后噪声降到 0.11 km/day，**"在推"阈值 0.5 km/day ≈ 4.5σ**（2026-10-17 由 0.8 下调，实测只多判 1 颗、无误判） | 「变轨中·点火 / 间歇 / 在轨」判定与升轨速率（`rr`） |
| **"慢慢爬"不能只靠速率判**：再加一条**与速率无关**的高度带判据 | 每天涨一点点、连着很多天累积起来的情况，任何单日速率阈值都抓不到；而**偏离该批工作高度 > ±30 km** 与速率无关，累计到阈值必然触发 | 「变轨中」的兜底（也是「间歇」态的判据）；代价是**不可见漂移上限 30 km**（1150 km 上约 2.6%） |
| **瞬时高度 ≠ 半长轴高度**：它是 **WGS-84 椭球高**（大地高）。对一条圆轨道，同样的地心距在赤道上空比极地上空**低 21.4 km**（= a−b），再叠加 **±a·e**（e≈2e-4 → ±1.4 km） | 升轨只在大半长轴上干净可见；瞬时高度沿轨道本来就会大幅起伏 —— "地球是椭球"这一项比偏心率大一个量级 | 信息窗"实时跳动"的高度读数（起伏是**物理真实**，不是抖动）；口径详见下方「三种高度」 |

### 🔐 关于第三方 CORS 代理（如实披露，V1.9.8）

浏览器直连 `celestrak.org` 时，若被跨域策略或网络环境挡住，页面会**退而尝试两个公共 CORS 代理**：

- `api.allorigins.win`
- `api.codetabs.com`

**这意味着什么，需要你知情**：走代理时，请求的目标 URL 与**你的 IP** 会经过这两个第三方服务。
本项目不发送任何个人信息，代理只用于转发公开的 TLE 请求；但**如果你不希望流量经过第三方**，
请在打开页面时保持直连可用（或使用「本地部署 + 定时任务」的方式，让数据在你自己的机器上更新）。

> 计划中：V1.9.8 之后会加一个「**仅直连**」开关（默认直连；失败时**询问**是否允许走代理），
> 并把当前的实际网络足迹写进页面的「关于」面板。
